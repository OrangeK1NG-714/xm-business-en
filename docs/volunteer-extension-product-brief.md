# 志愿招募浏览器插件：产品方案

更新：2026-10-19。根据最新需求，当前方向调整为原有志愿平台的浏览器插件；此前独立小程序与管理端的代码保留，暂停扩展。本文是产品方案，不表示插件或原平台对接已经完成。

## 目标与约束

使用者是负责志愿招募的管理老师。现在需要导出名单、逐人复制手机号通知、识别微信申请、催促入群，并在有人退出时另改文档、寻找替补。目标是把这些操作汇到按活动组织的跟进工作台，减少重复复制与核对。

原系统由外包维护，目前不依赖修改其源码或增加接口。第一版以管理员已有权限可见的页面数据及 Excel/CSV 为入口；不假设插件能够变更平台不支持的报名状态。统计用于单位内部留档。

## 优先流程

1. 为每个活动或场次建立工作卡：时间、地点、负责人、所需人数、进群说明、通知模板、确认截止时间。
2. 导入平台导出的名单，预览姓名、人员编号、手机号、活动和平台审核状态，确认归属后合并。以后可增加读取当前页面的适配器。
3. 逐条生成通知内容，绑定具体报名记录。可以按活动分批复制号码与文案，交给现有短信工具发送；只有存在发送结果时才标记“已发送”。
4. 分别记录通知、参加确认和入群情况。微信申请约定备注“活动编号 + 姓名 + 人员编号后四位”，在插件中检索匹配后人工标记入群。
5. 待办按截止时间呈现“尚未确认”“已确认但未入群”“需电话跟进”；记录联系时间、结果、下次跟进时间，已联系人员不重复催促。
6. 有人退出时保留原报名，填写退出原因与时间；关闭后续催办，列出该场次的人员缺口。管理员从合适候补中选择联系，确认后纳入工作名单。
7. 活动结束后核定出勤和分钟数，按所选日期导出人员活动明细、人员汇总、活动汇总。退出、缺席和仅审核通过的人员不自动累计时长。

## 状态设计

以“一人一次场次报名”为跟进对象，同一个人报两场活动须有两条记录。

| 维度 | 示例 | 数据来源 |
| --- | --- | --- |
| 平台审核 | 待审核、通过、未通过、平台取消 | 原平台读取或导入 |
| 参与意向 | 待确认、确认参加、确认退出 | 管理员登记；后续可接确认页 |
| 通知 | 未生成、待发送、已发送、受理、送达、失败、结果未知 | 实际人工记录或短信供应商结果 |
| 群联系 | 未添加、已添加、已入群、无需入群 | 管理员登记 |
| 跟进 | 无需跟进、待提醒、待电话、已处理 | 规则与联系记录 |
| 出勤 | 未核定、到场、缺席 | 活动后核定 |

“已发送”不推导出“收到”“确认参加”或“已入群”。平台审核通过但本地确认退出时，两项同时显示，并提示平台状态尚未变更。再次导入不会覆盖本地联系、退出、入群和出勤记录。

## 对具体痛点的改进

### 按活动通知与微信识别

通知队列展示收件人、活动、场次、群标识、模板与最近联系记录。批量操作先预览，按报名记录去重；同一手机号涉及多个活动时显示提醒，不误合并成一个活动。

文案示例：“张同学，你报名的【图书整理 A102，周六 09:00】已通过。请于周五 18:00 前联系负责人，微信申请备注【A102 张同学 1234】。”具体短信内容需要符合实际使用的短信工具模板。

同名、共用手机号、资料冲突时提示人工匹配。优先使用平台人员 ID / 报名 ID；其次使用单位人员编号。姓名、手机号仅作为匹配线索。

### 未回应与催办

以是否完成参加确认和入群作为跟进依据。浏览器开启时检查到期任务并展示待办；插件关闭期间不承诺持续执行。每天电话跟进前，只筛选仍未确认的人，记录通话结果，避免重新核对整份名单。

短信拦截无法由插件保证解决。后续如增加在线确认，可用单位已有问卷收集并导入结果；若要自动回写，则需要一个可被志愿者访问的确认页面及轻量服务。个人确认链接应使用不可猜测、可失效的令牌，页面只展示该条报名需要的信息，短信能否放链接以实际供应商模板为准。

### 退出与替补

退出属于报名记录的状态变更，不能以删除人员代替。插件的“确认退出”会停止催办、更新内部工作名单并显示缺口，但不会释放原平台名额或更改正式报名结果。

候补优先取自仍愿意参加且符合要求的人员。未通过者须区分“名额已满”和“不符合条件”，由管理员选择适合联系的人；不能把所有审核未通过者自动视为候补。推荐前检查时间冲突和已知退出意向，管理员确认联系与参加后才转正。需要平台审批的步骤保留为待办，不伪装为平台已通过。

## 第一版与后续增强

第一版优先交付：活动工作卡、Excel/CSV 导入及合并预览、通知文案与号码批量复制、微信备注检索、确认/入群标记、电话待办、退出与候补管理、内部留档导出及完整备份恢复。

第一版可以完全在管理员浏览器内运行，先验证每天是否能明显减少操作。页面读取适配器在看到真实页面后补齐，表格导入一直保留为稳定入口。

第二阶段按实际需要增加：页面名单读取、短信供应商对接、在线参加确认、多人协作。直接短信发送需要调用供应商的服务端接口，密钥存放在轻量服务端；浏览器扩展只提交已确认的发送任务。个人微信好友、群成员和短信已读状态不能假设可被普通浏览器插件读取。

## 技术选型与扩展边界

- 插件：WXT + React + TypeScript，Manifest V3；Chrome / Edge 侧栏作为主要入口。
- 本地数据：Dexie / IndexedDB；保存导入批次、活动、场次、报名、联系记录、候补、出勤与操作历史，支持备份恢复。
- 表格：ExcelJS 处理 xlsx，Papa Parse 处理 CSV；列名映射允许不同导出模板。
- 界面：沿用已有 React 与 Ant Design 组件，表单与表格复用现成组件。
- 平台适配器：只把平台可读取的资料转换为统一报名模型。导入层与跟进层分开，页面结构变化时不影响已保存的跟进记录。
- 通知适配器：文案/号码导出为第一版实现；后续独立接入真实短信任务、逐人发送结果与失败处理。
- 对账：保留来源、导入批次及时间。名单缺行不等于退出，避免把局部导出或分页缺失误判为取消。
- 默认本机持久化，不自动跨电脑同步；通过完整备份恢复迁移。多人共享与后台定时任务需要共享服务。

## 验收方式

先用虚构数据验证：同一人报不同活动可以独立跟进；重复导入不会重复通知或丢失本地备注；退出后不再催办；替补不会计作平台自动审核通过；未确认和未入群名单可分别筛选；跨日服务分钟和 Excel 汇总一致；重启浏览器仍保留记录，完整备份可恢复。

实际试用时比较一场活动的名单处理耗时、重复复制次数、电话跟进前的核对耗时、退出到替补确认的步骤数。是否继续扩展短信和确认服务，以这些改进是否成立为依据。

结论：建议优先做浏览器插件，先完成本地招募跟进流程。原平台读写适配、真实短信及在线确认分别作为后续接入点，不让第一版被外部系统接口阻塞。
